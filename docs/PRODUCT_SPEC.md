# StickTouch — 제품 기획 및 MVP 상세 명세

- **작성 목적:** 대화에서 확정한 기획의 장기 보존, 구현 기준 및 수용 테스트 정의
- **대상:** 브라우저 기반 Mac/노트북/모바일/태블릿 카메라 모션 게임
- **현재 상태:** 1차 웹 MVP 소스 구현, 모바일/PC 실기기 검증은 진행 전. 후속 게임 기획도 포함한다.
- **관련 문서:** [프로젝트 소개](../README.md) · [개발 지침](../AGENTS.md)

## 1. 제품 비전 및 원칙

플레이어의 실제 모습이 보이는 카메라 게임. 외부 장비 없이 손, 발, 머리, 몸통 같은 **신체 터치 포인트**로 화면 속 물체를 터뜨리거나 받거나 피한다. 관절은 스틱맨으로 표시할 수도 있고 숨길 수도 있다. 게임은 복잡한 3D 복원보다 **빠르고 정확하게 반응하는 재미**를 추구한다.

**이미 결정된 사항**
- 카메라 영상 전체를 그대로 사용 가능; 인물 분리/배경 제거 **불필요**.
- 스틱맨·가상 아이템·효과는 렌더링 레이어로 합성.
- 카메라 원본/카메라+스틱맨/스틱맨+가상 배경 등 **3개 표시 모드**.
- 관절 중심의 **원형 터치 영역**과 크기 조절, 원 표시 ON/OFF.
- 터치 영역을 게임별 신체 부위로 제한 가능.
- 복수 미니게임을 위해 추적/좌표 변환/충돌 엔진 재사용.
- 소스 변경은 **dev**, main 반영은 **fast-forward-only**.

**나중에 검증·결정할 사항**
- 각 원의 실제 기본 반지름과 최적 배율, 초기 활성 관절 구성.
- 각 게임의 라운드 시간·목표 수·스폰/낙하 속도·점수·난이도.
- UI 레이아웃, 모바일 세로/가로 우선순위, 사운드·아이콘 디자인.
- 다인 플레이, 손가락 상세 추적, 리더보드, 공유/수익화(현재 미정).
- 추적 성능 기준과 실제 지원 브라우저 범위(실기기 테스트 후 결정).

## 2. 사용자 경험 흐름

1. 시작 화면에서 게임 선택.
2. 카메라 권한 요청; 거부 또는 사용 불가능하면 원인과 해결 안내.
3. 카메라 미리보기에서 플레이어 감지 및 촬영 거리/프레이밍 확인.
4. 화면 모드와 터치 영역 크기 확인; 게임별 사용할 부위 안내.
5. 카운트다운 후 플레이. 점수·남은 시간·인식/일시정지 상태 표시.
6. 게임 종료 시 결과/다시 하기/다른 게임 선택.
7. 플레이 중 표시 모드/원 표시 옵션 전환과 일시정지 지원.

온보딩은 짧고 쉽게. 초기에는 가입을 요구하지 않는다(추후 결정 사항).

## 3. 게임 화면과 표시 레이어

### 3.1 모드

| 모드 | 레이어 구성 (아래 → 위) | 기본 동작 |
| --- | --- | --- |
| Camera | 실제 카메라 → 게임 물체 → UI/이펙트 | 추적은 계속, 스틱맨 숨김 |
| Camera + Stickman | 실제 카메라 → 관절선/점 → 게임 물체 → UI/이펙트 | 추적 스틱맨 확인 |
| Stickman | 게임별 가상 배경 → 관절선/점 → 게임 물체 → UI/이펙트 | 카메라 원본 숨김, 추적 지속 |

터치 원을 켜면 게임 오브젝트의 시인성을 해치지 않는 반투명 원/윤곽선을 관절 위치에 그린다. 원의 렌더링 순서는 가독성에 따라 조절할 수 있으나 판정은 변화하지 않는다.

**중요:** 표시 모드를 변경해도 카메라 스트림, 추정 결과, 충돌 좌표/판정, 스코어링이 리셋되지 않아야 한다.

### 3.2 영상 배치

- **Full Camera Layout:** 플레이어가 중앙에 보이도록 카메라 전체 영상을 화면에 채움. `object-fit: cover`가 만드는 잘림을 추적 좌표에 반영.
- **Bottom Camera Layout:** 과일 바구니 게임처럼 영상 **전체 직사각형**을 아래쪽에 작게 배치하고 그 위의 넓은 부분을 게임 배경/과일 낙하 공간으로 사용. *이 경우에도 세그멘테이션 불필요.*
- 스틱맨 모드에서는 카메라 원본이 없어도 같은 플레이어 위치/스케일로 관절을 배치한다. 별도의 가상 배경이 반드시 보인다.
- 전면/후면 카메라의 좌우 반전, 화면 회전, 세로/가로비, 게임 HUD 안전 영역을 처리한다.

### 3.3 미러링/좌표 처리 기준

- 추정 원본 관절 데이터와 렌더링 좌표 변환을 분리한다. 게임의 기준 좌표를 정규화된 2D 게임 공간으로 통일한다.
- 각 게임의 **CameraViewport** (x, y, width, height, scale mode, mirror flag)를 통해 좌표 변환.
- 화면에서 보이는 손 위치와 실제 히트박스 중심이 일치해야 한다. 영상 플립을 적용했다면 스틱맨·원·바구니에도 같은 수평 변환을 한다.
- 사용자 왼손/오른손 구분은 미러 표시 여부와 독립적으로 관리.
- 카메라가 공간을 잘라낼 때는 보이지 않는 부위의 충돌을 끈다. 단순 좌표 clamp로 화면 가장자리에 잘못된 타격을 생성하지 않는다.
- 프레임마다 캡처 시간과 추정 시간 차이를 추적하고 게임 루프와 동기화한다.

## 4. 자세 인식 및 터치 영역 모델

### 4.1 권장 입력 데이터 계약 (구현 제안)

```ts
type BodyPart =
  | "leftHand" | "rightHand"
  | "leftElbow" | "rightElbow"
  | "head" | "torso"
  | "leftKnee" | "rightKnee"
  | "leftFoot" | "rightFoot";

type Hitpoint = {
  part: BodyPart;
  x: number;           // 화면/게임 좌표 변환 결과
  y: number;
  confidence: number;  // 추정 신뢰도
  radius: number;      // 실효 판정 반지름
  active: boolean;     // 게임별 허용 여부
};

type PresentationMode = "camera" | "camera-stickman" | "stickman";
```

관절 추정기의 랜드마크를 바로 게임마다 읽는 대신 `PoseTracker → CoordinateMapper → HitpointEngine`에서 공통 데이터 계약으로 변환한다. 머리, 몸통 및 손/발은 모델 랜드마크와 파생 앵커 조합으로 정의할 수 있다(어떤 점을 사용할지는 추적 품질을 보고 결정).

### 4.2 반지름과 활성화

초기 계산식의 예:

```ts
effectiveRadius =
  baseRadiusByPart[part]
  * playerScaleFactor
  * (hitboxScalePercent / 100);
```

- 기본 배율 100%; 빠른 선택 70 / 100 / 150%; 프로토타입 슬라이더 50~200%.
- `playerScaleFactor`는 화면에서 추적되는 어깨 폭/몸통 크기 등으로 도출하고 극단 값은 제한. 정확한 식은 실기기에서 튜닝.
- `showHitpoints`는 **시각 표시만 제어**하고 `hitboxScalePercent`는 **실제 판정만 포함해** 반지름을 변경한다.
- 각 게임이 `activeParts`를 정의한다(예: 풍선 게임 손, 헤딩 게임 머리, 과일 게임 바구니).
- 낮은 신뢰도, 화면 밖, 여러 사람 중 대상 미확정, 장시간 추적 끊김에서는 해당 포인트를 비활성화한다.
- 게임 오브젝트가 원이고 포인트가 원일 때 충돌 예: 두 중심 거리 ≤ 두 반지름 합.
- 지속 접촉을 매 프레임 득점하지 않도록 hit-enter 감지, 대상 소멸 또는 쿨다운을 적용.

### 4.3 추적 불안정 처리

- 손 위치 떨림 방지를 위해 약한 스무딩 적용. 과도한 스무딩으로 반응성이 떨어지지 않게 확인.
- 순간 가려짐은 짧게 보정 가능하나, 너무 오래 추정이 끊기면 히트 포인트 제거/게임 일시정지 여부를 검토.
- 여러 사람 감지 시 MVP는 **한 명의 활성 플레이어**를 대상으로 하고, 선택 기준을 UI에 안내.
- 자세 인식 `z` 좌표를 카메라로부터의 정확한 실제 거리로 단정하지 않음. 현재 게임은 2D 충돌을 기본으로 한다.

## 5. 게임별 상세 설계

### 5.1 사방에서 날아오는 물체 터뜨리기

**핵심 경험:** 내가 화면 중심에 있고, 상/하/좌/우에서 다가오는 가상 아이템을 손/발 등으로 치면 터진다.

- 레이아웃: Full Camera, 중앙 플레이어, 게임 외곽에서 아이템 이동.
- 1차 입력: 양손; 추후 머리/양발/팔꿈치 및 위험 아이템 종류 옵션.
- 객체: `id`, 위치, 방향, 속도, 반경, 타입(일반/보너스/위험), 생존 상태.
- 판정: 활성 손 터치 원이 아이템의 원과 교차하면 타격 이벤트 1회 발생.
- 표현: 터지는 파티클, 점수 텍스트, 사운드, 짧은 타격 피드백.
- 난이도: 아이템 반경/속도/빈도 및 위험 아이템 비율.
- 주의: 예고 없이 얼굴로 물체가 돌진해 플레이어가 실제로 급하게 움직이지 않도록 안전한 게임 디자인.

**완료 기준**
- 표시 모드 3종 모두 같은 동작으로 같은 오브젝트를 터뜨릴 수 있음.
- 원 표시를 꺼도 판정이 동일함.
- 원 크기를 키우면 가상의 일반 목표물 허용 오차가 커짐.
- 하나의 아이템은 한 번만 점수 처리됨.
- 좌우 미러링 시 손 위치와 화면 타격이 일치함.

### 5.2 떨어지는 과일 바구니

**핵심 경험:** 내 카메라 모습이 화면 아래에 작게 보이고, 위에서 낙하하는 과일을 내 움직임과 연결된 바구니로 받는다.

- 레이아웃: Bottom Camera + 위쪽 게임 영역.
- 기본 바구니 조작: **양 손목 사이의 중점**. 양손 동시 추적이 어렵다면 몸통 중심에 붙이는 조작 또는 게임 시작 시 선택하는 모드로 폴백.
- 가상 바구니 위치는 *추적 좌표를 축소된 카메라 뷰포트에 적용한 결과*로 계산해야 한다. 별개 화면 좌표계를 섞지 않는다.
- 과일은 상단에서 낙하하고 바구니 히트 영역 안에 들어오면 획득. 낙하 실패/폭탄 접촉은 게임별 규칙으로 처리.
- 바구니 이미지는 실제 플레이어 앞에 오버레이될 수 있으나 사람 분리는 하지 않는다.
- 스틱맨 단독 모드에서도 축소된 플레이어 영역과 낙하 공간을 유지.

**완료 기준**
- 카메라가 아래쪽에서 축소돼도 바구니가 실제 손 움직임을 정확히 따라감.
- 화면비/미러/리사이즈 후에도 일관된 포착 판정.
- 양손이 안 잡힐 때 오작동 대신 안전한 폴백/안내.
- 과일 중복 점수 없음, 범위 밖의 과일 정리.

### 5.3 포즈/리듬

**핵심 경험:** 화면에서 지정한 목표 부위 위치에 몸을 가져다 대거나 정해진 포즈를 취하면 점수 획득.

- 활성 부위와 목표 위치/허용 시간/허용 반경을 게임 데이터로 관리.
- 홀드 동작일 경우 타이머, 단발 동작일 경우 진입 이벤트로 판정.
- 조명·추적 손실로 인한 억울한 실패를 최소화.

**완료 기준**
- 화면상의 목표와 실제 신체 위치가 일치.
- 올바른 부위만 점수에 반영.
- 입력이 끊길 때 중복 득점/무한 홀드가 발생하지 않음.

## 6. 기술 구조 제안

```text
CameraService
  └─ video frame / device state
       └─ PoseTracker (MediaPipe Pose Landmarker 검토)
            └─ landmark + confidence + timestamp
                 └─ CoordinateMapper (mirror / crop / viewport)
                      └─ HitpointEngine (active parts / radii / contacts)
                           └─ GameEngine (objects / rules / score)
                                └─ Renderer
                                     ├─ camera or virtual background
                                     ├─ stickman (optional)
                                     ├─ hitpoint circles (optional)
                                     └─ game objects / HUD
```

- UI/렌더/추적이 프레임레이트 차이 때문에 서로를 강제로 블로킹하지 않게 설계.
- 초기에는 Canvas 2D 렌더러로 충돌·지연 검증. 3D는 추후 필요할 때 추가.
- React + TypeScript + Vite는 개발 편의상 **제안**이며 실제 소스 분석 및 MVP 구현에서 결정.
- 코어 게임 루프는 시간 차 `deltaTime` 기반으로 작성해 프레임레이트에 따라 속도가 변하지 않도록 함.
- 게임 모듈은 `setup/update/onHit/render/cleanup` 같은 간결한 수명주기를 제공하도록 검토.
- 디버그 보기: 랜드마크 신뢰도, 인식 FPS, 렌더 FPS, 프레임 지연, 좌표 정합 정보.

## 7. 설정 구상

| 설정 | 초깃값 제안 | 비고 |
| --- | --- | --- |
| 표시 모드 | Camera + Stickman | 사용자 선택 저장 여부 추후 결정 |
| 터치 원 표시 | ON | 카메라만 모드에서도 독립적으로 선택 |
| 터치 반경 배율 | 100% | 70/100/150 프리셋, 50~200 슬라이더 검토 |
| 카메라 거울 모드 | 전면 카메라에서 기본 ON 검토 | 실제 화면과 판정 반드시 동기화 |
| 카메라 장치 | 사용자가 선택 가능한 장치 | 권한 거부/장치 없음 대응 |
| 캘리브레이션 | 시작 전 플레이어 인식 | 신체 크기와 사용 공간 확인 |
| 사운드 | ON(볼륨/음소거 제공) | 브라우저 자동재생 제약 고려 |

표시 모드/원 표시가 게임의 내부 판정 로직을 바꾸지 않는 것을 자동 테스트 대상으로 만든다.

## 8. 성능과 프라이버시

- **기본 처리 기기 내 수행**. 녹화/서버 전송/추적 이력 저장 기능을 MVP에 넣지 않는다.

## 11. Git 운영

- 개발 브랜치: `dev`.
- 기본/안정 브랜치: `main`.
- 직접 main에서 개발하지 않는다.
- 사용자가 main 반영을 요청하기 전에는 dev 변경을 main에 적용하지 않는다.
- strict fast-forward-only: `main`이 `dev`의 조상인지 확인하고 `git merge --ff-only origin/dev` 또는 비강제 ref 이동만 허용.
- GitHub의 일반 Merge/Squash/Rebase-Merge 버튼을 fast-forward로 **대체하지 않는다**.
- 비-fast-forward 상태일 경우 중지 후 문제 해결. force push 금지.
- main 반영 후 두 브랜치 SHA 일치 확인.

세부 규정은 [AGENTS.md](../AGENTS.md)의 **필수 Git 브랜치 규칙** 참고.


## 웹 MVP 기술 확정 및 1차 범위 — 2026-10-21

**하나의 게임 엔진 / 하나의 웹 앱 / 두 종류의 입력 디바이스.** 초기 화면에서 카메라 권한을 요청하고 `getUserMedia`로 내장 웹캠·USB 웹캠·모바일 전후면 카메라를 연다. 프레임을 MediaPipe Lite Pose Landmarker(Web, VIDEO 모드)로 분석하고, 정규화된 랜드마크와 신뢰도를 공통 좌표 변환기에 전달한다. 충돌 엔진 및 60초 풍선 게임은 기기 구분 없이 동일 모듈을 사용한다.

### 배포와 개발 워크플로
- React 19 / TypeScript / Vite / Canvas 2D. `npm run dev` → localhost에서 개발, `npm run check && npm run test && npm run build`로 검증.
- `dev`에서는 개발·GitHub Actions CI만 수행하며 Vercel 자동 Preview 배포를 비활성화한다. 모바일 개발 테스트는 Codespaces HTTPS 또는 로컬 HTTPS 터널을 사용한다. 정적 사이트 `dist`의 Vercel 자동 배포는 `main` 릴리스에 한정하며 서버 측 영상 처리는 불필요하다.
- 영상·랜드마크 업로드/녹화·DB 저장 없음. MediaPipe 런타임(WASM)과 모델 초기 다운로드는 외부 정적 URL에 의존. 네트워크 차단 시 친절한 오류 표시.
- 기본 전면카메라 사용 및 가로 화면 권장. 화면 미러링/cover crop은 뷰포트 변환에 일괄 적용.
- 카메라 없는 경우, 보안 컨텍스트(HTTPS/localhost)가 아닌 경우, 권한 거절 시 해결 메시지와 재시도를 지원.

### 구현 우선순위
1. 장치의 카메라 허용·재시작·종료, 모델 GPU→CPU 폴백.
2. 세 가지 렌더링 모드와 원 표시 ON/OFF 독립성 검증.
3. 랜드마크 신뢰도·화면 밖 좌표 배제·원 크기(50–200%)·한 풍선 1회 점수.
4. 60초 풍선 터뜨리기, 카운트다운, 결과/재시작.
5. 실제 iOS Safari·Android Chrome·Mac Chrome/Safari에서 조명/거리/CPU/FPS 실측.

### 1차 이후에 별도 검증할 것
모바일 기기별 실제 렌더링/추론 지연, PWA 오프라인/서비스워커, 기기 카메라별 고급 선택, 게임 포즈 중단 후 자동 복귀, 다른 미니게임, 게임 내 소리와 리더보드. **자동 테스트 통과를 실기기 카메라 품질 보증으로 간주하지 않는다.**

## 2026-10-21 — 손바닥 정밀 추적(2차 실험 구현)

- 손 터치 앵커는 단순 Pose 손목 15/16이 아니라 **Hand Landmarker의 손목 0 및 5/9/13/17 MCP 지점의 가중 중심**이다.
- 동일 프레임의 카메라 정규화 좌표에서 Hand 손목을 Pose 좌/우 손목과 거리 기반 매칭하고 **한 손을 두 포인트에 중복 배정하지 않는다**. 좌우 카메라 미러링은 매칭 이후 공통 `CoordinateMapper`에서 수행한다.
- Pose 손목의 인식 신뢰도가 떨어지거나 프레임 밖이면 해당 손을 게임 입력에서 제외한다. Hand 모델/손 인식 실패 시에는 Pose 손가락(17/19, 18/20) 또는 전완 연장 방향을 사용한다. 추적 전환 시 보간으로 점프를 줄인다.
- UI 토글 **손바닥 정밀 추적** 기본 ON, OFF는 Pose 전용 비교 모드다. Hand 모델 GPU→CPU 폴백 이후 모두 실패해도 Pose만으로 게임 계속 실행.
- Pose는 약 95ms 간격, Hand는 기본 약 160ms 간격으로 추론하며 Hand 실행 비용이 높으면 450ms까지 자동으로 간격을 늘린다. Canvas는 별도 requestAnimationFrame으로 렌더링. **실기기 프로파일링이 끝난 확정 최적값이 아니라 시험값**이다.
- 회귀 테스트에 손바닥 중심, Pose 손목 연결, 양손 교차 대응, Hand 실패시 Pose 폴백, 미러링 좌표, 보간을 추가한다.
- Hand/Pose 영상 추론은 클라이언트에서 실행하고 서버 업로드/녹화는 없음. CDN 및 모델 다운로드를 위한 인터넷은 필요함.


## 손바닥 추적 ON/OFF 동작과 진단 표시 (2026-10-21)

**Hand 모델 사용 ON**은 `Hand Landmarker`를 실행해 손당 21개 랜드마크 기반 손바닥 중심을 우선 적용하며, 인식에 실패하면 Pose로 추정합니다. **OFF**는 Hand 추론을 멈추지만, Pose의 손목·손가락·팔꿈치 좌표를 이용해 **계속 손바닥 중심을 추정합니다**. 따라서 둘 다 손바닥에 터치 원이 표시되는 것이 정상입니다.

실제 비교를 위해 각 손의 현재 입력 소스(HAND / POSE / 인식 없음)를 설정 패널에 표시합니다. **손의 터치 원이 청록색이면 HAND, 주황색이면 POSE 추정**입니다. 이는 모델이 로드됐는지 여부가 아니라 그 프레임의 실제 게임 앵커 선택을 기준으로 합니다. 스틱맨 선은 계속 Pose에서 가져오며, 토글을 꺼도 정밀 모델 객체는 현재 카메라 세션 동안 메모리에 있지만 추론은 중단됩니다.

평소 자세에서 두 모델의 위치가 비슷할 수 있으며, 추가 손 모델의 필요성은 다양한 각도/가림/반응속도/FPS를 실기기에서 비교해 판단합니다. `main` 병합은 별도 요청에 따른 fast-forward-only 규칙을 유지합니다.

## Vercel 자동 배포 정책 (2026-10-21)

저장소 루트 `vercel.json`에서 **`git.deploymentEnabled.dev = false`**, **`git.deploymentEnabled.main = true`**로 고정합니다. `dev` 푸시는 **Vercel에서 자동 Deployment/Build를 생성하지 않고**, `main` 푸시만 자동 프로덕션 배포합니다. 이는 단순 `ignoreCommand` (빌드 요청 후 skip)보다 낭비가 적습니다.

- 기능 개발: `dev`에서 작업하고 **GitHub Actions 테스트·TypeScript 검사·빌드는 계속 실행**합니다(이 CI는 Vercel 빌드 쿼터와 별개).
- 실기기 개발 테스트: localhost / GitHub Codespaces HTTPS / 사용자에게 승인된 임시 HTTPS 터널. `dev` 자동 Vercel Preview 링크는 만들어지지 않습니다.
- 릴리스: 검증된 `dev` SHA를 사용자가 승인하면 `main`으로 **fast-forward-only** 반영하고 Vercel 자동 배포합니다.
- 보충: 해당 규칙은 이 프로젝트의 Git 연동 자동 배포 정책입니다. **명시적 수동 배포, Deployment Hook, 다른 프로젝트의 자동 빌드**까지 차단하는 것은 아닙니다.

근거: [Vercel Git configuration](https://vercel.com/docs/project-configuration/git-configuration).

## 2026-10-21 Game Feel Engine 통합 설계

## 2026-10-21 구현 업데이트 (dev)

### 과일 바구니
- 60초, 떨어지는 과일 수집, 놓치면 콤보 종료, 폭탄을 바구니에 받으면 피해 처리.
- 하단 축소 비디오(직사각형, 배경 제거 없음)는 `contain`으로 원본 전체를 보존하고 화면 미러링 및 추적 위치는 같은 변환을 사용. 양손이 있으면 x좌표 평균, 한손이면 그 위치로 바구니를 좌우 이동.
- 카메라로 손바닥이 검출되지 않으면 물리/라운드 시간 정지, 복구 시 재개. 최고 점수와 점수 HUD는 공통 엔진이 계산.

### 포즈 챌린지
- 상대 관절 위치로 5개 자세를 판정하고 지정 자세를 연속 0.85초 유지해 성공. 대상 자세마다 최대 8초이며 빨리 성공하면 더 높은 기본 점수. 목표 자세 팝업에 포즈 그림과 유지 미터를 표시.
- 관절이 인식 불충분한 프레임은 타이머·실패를 진행하지 않음. 전신 스켈레톤과 2D 추정만 사용; 절대거리 측정 없이 작동.

두 게임은 카탈로그의 `available` 상태로 전환되며 기존 카메라/스틱맨/일시정지/QuickSettings/GameFeel/audio/effects/record의 같은 런타임을 공유. 관련 순수 단위 테스트를 추가했으며 데스크톱/모바일 실기기 검증은 추가 작업이다.

## 2026-10-21 — 과일 바구니 손 이동 감도 (개발 반영)

플레이 감도 개선: 과일 바구니는 손 위치를 직접 접촉 판정하는 게임이 아니라 좌우 조향 입력으로 사용한다. 원본 영상의 좌우 30~70% 범위에 해당하는 손의 평균 X 좌표를 게임 화면의 0~100%로 선형 확장한다. 이 범위 밖에서는 바구니가 양 끝에 머문다. 카메라 영상 미러링 및 `contain` 레이아웃의 실제 보이는 영상 좌표를 먼저 계산한 뒤 확대한다. 과일 판정 및 바구니 화면 경계 제한은 기존과 동일하다. 타 게임의 터치 좌표와 기본 배율에는 영향을 주지 않는다.

자동 테스트는 미러 유무, 양손 평균 및 한손 입력, 정상 범위/초과 범위, 바구니 양쪽 제한을 확인한다. 실제 어린이·성인/PC·모바일 카메라로 편안한 조작 폭을 확인하고 필요하다면 게임별 감도 설정을 추가한다.
